## 1. Overview

DNDApp is a campaign-memory tool for a D&D group.

1. During a session (played over Discord), players use the **web page** (served by the DNDApp server) to **take private notes**. Each note is sent to the server and archived immediately.
2. The session is recorded, and separate speech-to-text software produces **one timestamped transcript**.
3. The transcript is uploaded **with its session number and the date it was played**, by the DM on their **Sessions** tab, choosing which of their campaigns it's for (or through the API by an account with the `dm` role). The date is what ties it to the notes players took that day. The server archives it permanently. Then an AI **archivist** reads the transcript plus that date's player notes and updates the campaign's **knowledge base**. The archivist has full authority over the knowledge base and organises it however it judges best, including **who knows what**.
4. Each player keeps their **character sheet** on the web page (§6.4).
5. Players use the web page to **ask questions** ("How much do we still owe Brother Hal?"). Answers cite the session and timestamp, and only use what that player's character should know.

The app's two core functions are **asking questions** and **taking notes during the session**. A basic UI for both exists (§3.3); it will be refined with real use.

This is a personal project for a small group of friends. It is not sold and players don't pay for it.

**People and roles:**
- **Host / project owner (Kenny):** runs the server on his machine and owns the admin login (management only). He is **not** the DM. He plays through a separate, ordinary player account.
- **Admin login:** for managing the server (accounts, campaigns, roles, session uploads). It isn't in any campaign, so it can't ask questions or take notes. It passes DM checks in the API (that's how it uploads).
- **DM:** a separate person, with role `dm` in a campaign (set on the admin screen). The DM can do what's built, as this spec describes; more may come. The DM can't manage accounts.
- **Players:** role `player`. One account can be in several campaigns, with a different role and character in each.

Hard design problems:

- **Scale over time.** By session 200 the transcripts won't fit in any context window. Answers come from an AI-maintained knowledge base plus targeted search, never the whole history (§5).
- **Being able to start over.** Everything except the archive can be thrown away and regenerated from it (§4.3).
- **Who knows what.** Players miss sessions, get whispered secrets, and keep private notes. Q&A must not leak (§5.5), and campaigns must not mix (§5.4).

## 2. Constraints

- **All JavaScript.** Node.js for the server; a plain web page (HTML/CSS/JS, no build step) for players. Every response carries `X-Page-Version`, a fingerprint of the page's files and the modules it imports (`pageVersion` in `server/src/app.js`, live streams included); the page (`api.js`) reloads when it changes, after the person leaves any field they're typing in or the tab is hidden. Plain JS (ES modules), with JSDoc types where useful. npm packages are welcome.
- **Self-hosted.** The server runs on the host's own machine (Kenny's). No cloud backend of our own.
- **Thin client.** The web page only talks to the DNDApp server. It sends what players type (questions, notes, sheet edits) and displays results. It never processes, indexes or stores campaign data (only the login token, in the browser), and never calls the AI. One deliberate exception: the character sheet's rules (`packages/shared/src/sheet.js`, plain arithmetic) also run in the page so automatic values update while typing; the server runs the same file and stays the authority on what's saved.
- **Archive first.** Transcripts, player notes, DM corrections and accounts are archived as plain files and never modified. Everything else is derived and can be regenerated.
- **The AI owns the knowledge base.** No human reads it directly, so it doesn't need to be human-friendly. The archivist can create, restructure, merge and delete freely.
- **Claude via the host's Claude Code.** By default all AI work runs through Claude Code on the host (Claude Agent SDK), using the host's Claude subscription. The Anthropic API is a config switch away (§3.5).
- **Recording and transcription are out of scope.** DNDApp starts from a finished transcript file.

## 3. Architecture

```
 During the session:  web page ── POST /notes ──►  archive + private search index
 After the session:   transcript + date ── upload ──►  archive
                                                         │
                                       job queue ── archivist agent (full write access)
                                                         │   reads: transcript, that date's notes,
                                                         │          roster, attendance, its guide
                                                         ▼
                                                   knowledge base (records with known_by)
                                                         │
 Any time:            web page ── POST /ask ──►  Q&A agent (read-only, filtered to the asker)
```

### 3.2 Server

- Node.js (22+; developed on 24) with **Fastify**.
- Native modules (`better-sqlite3`, `sharp`, `@napi-rs/canvas`, `onnxruntime-node`) must come prebuilt; the host isn't expected to have a compiler or Python. Install with `npm install --ignore-scripts`, because npm 11 otherwise tries to compile `better-sqlite3` (see HANDOFF "Getting running on a new machine").
- **SQLite** (`better-sqlite3`), one file. FTS5 for keyword search; vectors as blobs, searched by brute force in memory.
- One background job at a time, in order (the archivist builds each session on the last). Interrupted jobs resume after a restart.

### 3.4 Networking

**Decision: Cloudflare Tunnel** with a cheap domain, using Cloudflare's free plan. The domain is **`thepartyledger.fyi`** (owner's pick, 2026-10-13, instead of the numbers-only `.xyz` first planned), registered with Cloudflare Registrar. A tunnel managed from the Cloudflare dashboard sends it and `www.` to `http://127.0.0.1:4400`; `cloudflared` runs on the host as a Windows service; the zone forces https (README, "The public address"). No extra gate in front of the site (owner, 2026-10-13: the app's own login is enough; Cloudflare Access would have been the built-in one). `cloudflared` on the host connects out to Cloudflare: no port forwarding, no static IP, home IP hidden. The server listens only on `127.0.0.1`. Every request except `/health`, `/login` and the web page's files needs a login. **`PUBLIC_URL`** (config/`.env`) is the single place the public address is set; it's a placeholder until the domain is bought. HTTPS JSON plus SSE for job progress and streamed answers.

Hardening (2026-10-07 audit): every response carries a Content-Security-Policy (own scripts only, no framing), `X-Frame-Options`, `nosniff`, `Referrer-Policy: no-referrer` and, with an https `PUBLIC_URL`, HSTS. Bodies are limited to 1 MB except upload routes (`MAX_UPLOAD_MB`). Logins are limited per name and per address (`TRUST_PROXY=loopback` so the tunnel's forwarded address is believed). Live streams are capped per login and re-check the login and membership with every update and keep-alive. Unexpected errors (file system, database, programming) reach people only as a general message; processing errors reach players only as "failed".

Rejected: Tailscale (each player installs it), port forwarding (CGNAT, exposes home IP), SSH (would give players host access).

## 4. Data

### 4.1 Inputs

**Transcript**: one plain-text file per session, uploaded with a session number and the date played (`YYYY-MM-DD`):

```
[HH:MM:SS] Speaker Name: what they said
```

Also accepted: `[MM:SS]`, fractional seconds, no brackets, `0:01:30 - Name: text`. Lines without a timestamp join the previous one. If the real recorder's format differs, add an adapter in `packages/shared/src/transcript.js`. **No real sample has been tested yet.**

**Speaker map**: transcript name → display name (`Thorin (Sam)`) **and the account** (`user_id`). Attendance and privacy depend on the account link.

**Glossary**: correct spellings and their speech-to-text misspellings, fixed before anything else sees the text.

**Player notes**: free text, private to the author. Each note has a `session_date`: today by default, and notes written before 06:00 count towards the previous day. A note links to the session uploaded with the same date. The author can edit or delete a note; the archive keeps every version (an edit or delete is a later line with the same id), and changes made after the session was processed reach the archivist between sessions (§5.2).

**DM corrections**: plain words ("the innkeeper is Brother Hal, not Hall"). Answering one of the archivist's questions creates a correction. The DM writes both on the Archivist tab.

**Character sheets** and **handouts** also reach the archivist, between sessions (§5.2).

### 4.3 Archive, restore and rebuild

The server runs on one data folder: `data/` (`DATA_DIR`) normally, or with `DATA_SET=example` (owner, 2026-10-28: "a toggle somewhere, like the config, that switches between the example data and real data") `data-example/` (`EXAMPLE_DATA_DIR`), which it seeds with the example campaign the first time it starts there (`src/example/`). The two never mix; only the embedding model (`models/`) is shared, from the real folder. The example holds nothing from play (no sessions, notes, knowledge base, proposals, handouts given, rolls or rests): that comes from feeding its transcripts in.

```
data/archive/
  _server/accounts.json                users incl. password hashes (passwords survive DB loss)
  <campaign>/
    campaign.json, members.json
    speakers.json, glossary.json      (+ history/)
    settings.json                     the DM's campaign settings, with when they changed (+ history/)
    corrections.jsonl                 append-only
    player-notes/<YYYY-MM-DD>.jsonl   append-only; an edit or delete is a later line with the same id
    character-sheets/<user id>.jsonl  append-only: each save's changes to the player's first character (first line = whole sheet)
    character-sheets/<user id>-<n>.jsonl  the same for their character number n (2, 3, …)
    character-sheets/<user id>.characters.jsonl  append-only: which character is active and which are deleted (the whole record each time; none for a player with one character)

    maps/<id>/changes.jsonl           append-only: each change to that map (first line = whole map)
    maps/<id>/source.pdf              the PDF, when the map is a page of one
    maps/<id>/variant-<v>-original.<ext>  another picture of the map, as uploaded (+ variant-<v>.<ext>, stretched to the map's size)
    maps/<id>/pins/<user id>.jsonl    append-only: someone's private pins on that map (the whole list each time)
    maps/<id>/tokens/<file>           a picture the DM gave an NPC or enemy token, as uploaded
    handouts/<id>/<picture>           a handout's picture, as uploaded
    handouts/<id>/changes.jsonl       append-only: the whole handout after each change
    wiki/<id>/changes.jsonl           append-only: the whole wiki page after each change (its history)
    wiki/proposals.jsonl              append-only: the AI's proposed wiki changes, the whole proposal after each change

    creatures/<id>/changes.jsonl      append-only: the whole creature after each change
    items/<id>/<picture>              a picture for one of the DM's items, as uploaded
    items/<id>/changes.jsonl          append-only: the whole item after each change
    merchants/<id>/<picture>          a merchant's picture, as uploaded
    merchants/<id>/changes.jsonl      append-only: the whole merchant (stock, prices, recent sales) after each change

    map_assets/<id>/changes.jsonl     append-only: the whole asset after each change
```

- **Deleting a campaign** removes it and everything derived or mirrored from it from the database (foreign-key cascades), but never touches the archive: the folder gets `deleted.json` and restore skips it. New campaigns never reuse an existing archive folder's slug. Undo by hand: remove the marker, restart, rebuild.
- A transcript can never be replaced (different bytes for an existing session number → 409).
- **Restore:** on start-up, accounts, campaigns, members, campaign settings, sessions, speakers, glossary, corrections, notes (with their edits and deletes), character sheets and maps (both replayed from their change lines), character pictures, handouts, the DM's creatures, rests the DM called, items, merchants, the DM's map creator assets and stamps, and private map pins missing from the database are restored from the archive, and notes are re-indexed. Then run a rebuild to regenerate the knowledge base.
- **Rebuild:** `npm run rebuild -- --campaign <id> --yes` (or `POST /rebuild`) wipes all derived data, re-indexes notes, then replays every session in order, each correction right after the session it was made against. Sheet changes and handouts are read in time order between the sessions (those from before a session's day, before it; the rest at the end). The archivist is non-deterministic, so a rebuild gives an equivalent knowledge base, not an identical one.
- Bump `PIPELINE_VERSION` (now 23, since the AI proposes wiki changes, 2026-10-21) when prompts, tools or the memory design change.

## 5. Knowledge base and Q&A (core design)

### 5.1 Knowledge base records

Each record has: free-form `kind`, `title`, `body` (free text), `data` (free-form JSON), `status`, `tags`, `sources` (citations), `known_by` (NULL = everyone, or a list of user ids), `pinned`, and first/last session. The archivist chooses the kinds and conventions, and records them in a **guide** (a reserved record) that it reads at the start of every run and that Q&A sees too.

Limits: 8,000 tokens per record (`KB_MAX_RECORD_TOKENS`; past it the archivist splits the record, and is told never to shorten one); pinned records share a 6,000-token budget, since they go into every question. Violations come back to the archivist as errors it can fix.

**Nothing is cut short** (owner, 2026-10-14: "No truncating or shortening. We can make the databases … as complicated as large as we like, as long as they're usable. What matters is speed and accuracy"). Every tool result for the archivist and for Q&A is built from whole pieces (records, transcript chunks, transcript lines, list lines) up to a size (`fit.js`): the first piece always comes whole, and the pieces that don't fit are named at the end with the tool to fetch them; `list_records` pages with `offset`, `read_transcript` stops at a whole line and says where to continue. The archivist's budget is `ARCHIVIST_MAX_TOOL_RESULT_TOKENS` (24,000), Q&A's `QA_MAX_TOOL_RESULT_TOKENS` (5,000). Claude Code's own limit on a tool result is raised (`MAX_MCP_OUTPUT_TOKENS`) so it never cuts one either.

**Search over long text.** The local embedding model reads only the first ~256 words it's given, so every search doc (record, transcript chunk, note) is embedded in overlapping windows of 150 words (each with the doc's title), stored end to end in its `embedding`, and a doc scores by its best window. Docs embedded the old way (tagged with the bare model name) are embedded again in the background on start-up (`search.reembedStale`).

In the first real run, it created kinds `summary`, `session`, `pc`, `npc`, `faction`, `place`, `item`, `debt`, `quest`, `clue`, with statuses such as `owed / partially paid / paid` for debts.

### 5.2 The archivist (processing)

Per session (job `ingest`):

1. Parse, apply speaker map and glossary.
2. **Attendance**: accounts linked to transcript speakers who spoke, plus anyone who took notes that day, plus DMs. If no speaker is linked to an account, everyone is assumed present (and the archivist is told so).
3. Chunk and index the transcript. Chunks are visible only to attendees.
4. **Archivist run** (agent). It gets the roster (user ids, names, characters, transcript names), its guide, pinned records, record counts, open DM questions, the session number/date/attendance, that date's player notes (author + time written), and the full transcript (up to 200k tokens; longer ones are read in parts with `read_transcript`).
5. Snapshot the run (report, journal, full knowledge base, questions) to the archive.

Per DM correction (job `correct`): the archivist gets the correction and its state, and applies it.

Between sessions (job `updates`, `kb/updates.js`; owner's request, 2026-10-08: "the AI should get the sheet when it's made, and any changes as well as when that change happened"): the archivist gets
- **character sheets**: a new sheet in full (what the player entered, plus the numbers worked out from it, every text field whole, each item with its description, inspiration, hit dice spent, death saves, spell slots used, and the text of the player's own spells), then each change since it last read that sheet, with the time it was saved (`[2026-10-08 14:03] classes[Fighter].level: 3 → 4`). Saves of the same field within 10 minutes count as one change; a field changed and changed back is no change. Read from the archive, which keeps every save with its time, so a rebuild sees the same changes.
- **late note changes**: notes written, edited or deleted after their session was processed (an edit says what it said before; a delete says to drop what only that note supported). Everything comes in full; a long text that changed (a note, a backstory) gives the lines that changed, word for word, and the line before them, rather than the whole text twice. Notes for sessions not processed yet wait for the session.
- **handouts** given, changed or taken back, with who got them. The archivist can't see pictures, so each handout picture is first read by the AI (`handout:picture`, the `import` task: any writing word for word, then everything it shows in full detail, kept in memory so a picture is read once per server run); if that read fails, the whole run fails and is tried again later, so no handout is skipped.
The job runs once nothing has changed for `ARCHIVIST_UPDATES_DELAY_MINUTES` (default 10), so filling in a sheet is one run, not one per keystroke; anything left from before a restart is picked up on start-up. With nothing new, no AI call is made. A mark (`archivist_marks`) says how far it has read. The archivist is told sheets are private to their player (anything only on a sheet stays known by that player, unless play shows others know it) and handouts are known by the players who got them.

**Archivist tools** (full write access): `search_kb`, `list_records`, `get_records`, `create_record`, `update_record`, `delete_record`, `update_guide`, `ask_dm`, `search_transcript`, `read_transcript`, `read_player_notes`. Every write needs a reason and is journalled.

**Instructions, in summary:** track everything useful, especially anything with changing state (debts, promises, quests, inventory, status, relationships); **be thorough**: archive every detail the sources give, not a summary (names and spellings, numbers, prices, who said what, descriptions, what was tried), with anything that may matter in its exact words (deals, oaths, prophecies, riddles, inscriptions, letters) kept word for word, since size is not a concern; **never lose information** when updating, merging, splitting or restructuring, and keep the history of changed states; split a record that nears the size limit rather than shortening it; go through the material start to end and check it again before finishing; update rather than duplicate; merge, restructure and delete freely; cite sources; keep pinned records short (they point to the full records); DM narration and corrections are authoritative; player notes are perspective, not fact; ask the DM about conflicts it can't resolve rather than guess.

### 5.3 Q&A

0. **Two ways of answering** (owner, 2026-10-21: "Ask is way too slow… Maybe it is being too thorough for some stuff?"). Before any AI call, `qa/route.js` decides by rules alone (no AI): **quick** for a general D&D lookup, **full** for everything else. Quick needs a D&D signal (a rules word such as spell, item, condition, stat block, "dnd", or the shape "what is a…", "what does … do", "how does … work") and nothing pointing at the campaign: no "we", "our", "party", "session", "the DM" and the like, no first person outside rules phrasing ("can I", "do I" are rules questions; "my character", "what did I" aren't), no who / where / when / why, nothing in the past tense, and no name of a record, wiki page, character or (for the DM) saved creature **that this asker can see** (so the way a question is answered gives nothing away). A follow-up in a conversation answered the full way stays full. When unsure, full. The quick way runs **the same model** at `EFFORT_QA_QUICK` (default `low`; the full way stays at `EFFORT_QA`, `medium`), with at most `QA_QUICK_MAX_TOOL_CALLS` (4) lookups, a shorter prompt without the archivist's guide or pinned records, a pre-search of the records and wiki only (`QA_QUICK_PRESEARCH_TOKENS`, 1,500), the books only when the exact wording or numbers matter, and a short answer. A quick answer on the page has **Look it up properly**, which asks the same question again the full way (`mode: 'thorough'`); `mode: 'quick'` forces the quick way. `qa_log.path` records which way each answer went. **Which model** (owner, 2026-10-28: "quickly decide if it's stored in the data we have, or needs looking up, then assign a fast model if we have it, or more intelligent model if we don't"): after the automatic search, `pickModel` (`qa/route.js`, no AI) sends the quick way, and a full-way question that names a record or wiki page the automatic search put in front of the model, to the faster model (`MODEL_QA_FAST`, default `claude-sonnet-5-5`; `off` for `MODEL_QA` everywhere); everything else (nothing named, or the search didn't bring its record) and every `mode: 'thorough'` go to `MODEL_QA`. The faster model keeps every tool. Its full-way answers also carry **Look it up properly** ("Quick answer from the records"). An AI deciding this would cost a call of its own, so it's rules only. While the books are still being read after a restart, a quick question doesn't wait for them (it's answered without them); a full one does.
1. **Pre-search** (free): the server searches the knowledge base, transcripts and the asker's own notes for the question and sends the results with it: the best of each kind first, then the next best, each whole (never cut), up to ~5,000 tokens (`QA_PRESEARCH_TOKENS`), then the names of what else matched.
2. **System prompt**: rules, who is asking, the archivist's guide, and pinned records the asker may see. The model first decides whether the question is **general D&D knowledge** (rules, spells, a standard creature's stat block) or **about this campaign**. General questions are welcome and answered straight from the model's own 5e knowledge with no tool calls (noting any house rule the pre-search turned up); campaign questions are researched and answered only from the sources.
3. **Tools** (read-only, filtered to the asker): `search_kb`, `list_records`, `get_records`, `list_sessions`, `search_transcript`, `read_transcript`, `search_my_notes`.
3a. **The group's books** (only when `BOOKS_DIR` has PDFs; they're listed in the system prompt with the year each was first printed, read from its credits page, and their page ranges): `search_books` (1–8 terms the model writes itself, not the player's sentence; keyword search over the page text held in memory, rarer terms and pages matching several terms rank higher, a heading counts double and a heading that is the term counts most (capitalised lines, the PDF's bookmarks, and short lines compared without spaces for headings the OCR split), terms of 3 letters or fewer match whole words only, longer ones the start of a word, OCR mix-ups and line-end hyphens are folded; returns up to 8 pages with a snippet; an unknown or ambiguous book name is an error naming the books), `read_book` (1–2 pages, never cut short), `book_contents` (the PDF's bookmarks, else the capitalised headings on each page; when too long for a tool result, the deepest levels are dropped first). PDF text is joined by position, so an OCR layer's word pieces read as words. Pages are numbered as printed when the page numbers can be read (lines that are only a number, else numbers in running headers and footers; a consistent offset from the PDF's numbering), else by PDF page. Titles are the file name up to any " -- " (downloaded files' extras). No database and nothing stored: the text is read from the PDFs at start-up; a PDF with mostly empty pages is logged as needing OCR. With books, **every rules question asked the full way is looked up in them** (the quick way only when the wording or numbers matter, item 0) (rules, conditions, spells, features, items, tables, stat blocks): search in the first turn, read the page before answering, follow index hits, and say so when the books don't cover it (then answer from memory). Editions: books first printed 2024 or later use the 2024 rules, earlier ones the 2014 rules; never mixed in one answer; the group's edition is the campaign's setting when the DM has chosen one (§6.10), else taken from their Player's Handbook (both or neither: what the records say, else the campaign's fallback edition from `editions.js`, and the answer says so in a few words). The edition is always stated in the prompt, both ways, with or without books, and **answers are for that edition only**: the model doesn't say how the other edition differs or compare them unless the player asks (owner, 2026-10-21: "Just what is relevant to the edition we are playing"). When the edition is known for sure (the DM's setting, `REST_RULES`, or one Player's Handbook), `search_books` leaves out the other edition's books (books of no known edition stay in) and searches them all only when that finds nothing; a book named in the call is always searched. Vague questions: it works out which rule is meant, searches with the book's terms plus synonyms, searches again or browses the contents if that misses, and asks when it can't tell. Book pages are cited as `(Player's Handbook p. 195)`; they aren't campaign sources, so there's no `[S…]` citation or evidence for them. The books aren't campaign data, so everyone in any campaign may search them.
3b. **The DM's creatures** (owner's request, 2026-10-09; only when the asker's role is `dm`): the system prompt lists the DM's saved creatures (name, kind, whether it has a stat block) with the rule that a saved creature of that name is the DM's own version and beats the books, the records and the model's knowledge; creatures named in the question ("Goblin 3", "goblins" match "Goblin") are put in full after the question (`<my_creatures>`); `get_my_creatures` gives others in full (stat block and where it came from, hit points, size, speed, darkvision, the DM's notes). Players never get the list, the block or the tool.
3c. **The DM's wiki** (§6.11; only when the asker can see some of it): `search_wiki` and `read_wiki_page`, and the pre-search includes wiki parts. The DM gets every part, marked with who it's available to; a player gets only the parts available to them, found by title only (other names can be secrets). Text always comes from the page as it is now, filtered for the asker, never from the search index. Cited as (wiki: Page title). A player with nothing available gets no tools and no mention of a wiki.
4. **Answer** with citations `[S12]`, `[S12 01:23:45]`, `[S12 01:23:45-01:24:10]`. Evidence (the cited transcript lines) is attached server-side, only for sessions the asker attended.
5. Follow-ups include the last 3 Q&As and the last answer's sources.
6. **Formatting:** answers are markdown, optionally with HTML (tables, stat blocks with `class="stat-block"`). The page renders them with `marked` and sanitises with DOMPurify to an allowlist (no links, images, scripts or style attributes), then turns citations into buttons, including inside tables. Stat blocks and records on the Map and Creatures tabs go through the same cleaner (`web/public/markdown.js`). Both libraries are served from `node_modules` at `/vendor/marked.js` and `/vendor/purify.js`.

Streaming events (`POST /campaigns/:cid/ask` `{question, conversationId?, mode?}`, SSE): `conversation`, `turn`, `tool`, `text`, `done` (with `path`: `quick` or `full`, and `fast`: whether the faster model answered), `error`.

**Timings** (2026-10-21): every answer writes one line to the server log (`data/server.log`): `Ask answered (quick) in 4100 ms` with `ask: {path, why, effort, model, model_why, system_chars, prompt_chars, prep_ms, books_wait_ms, first_turn_ms, first_text_ms, turns, tools: [{name, at_ms, ms}], total_ms}`. No question text (it can be private). Research and measurements: [docs/notes/ask-speed.md](docs/notes/ask-speed.md).

**Claude Code's start-up** (the default provider): every AI call starts a Claude Code process. It's started with `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1` (no telemetry, error reports or update checks), which took ~2.9 s → ~0.65 s to the point where it's ready, measured 2026-10-21; `CLAUDE_CODE_QUIET_START=off` turns it off.

### 5.4 Campaigns are separate

Every campaign has its own sessions, transcripts, knowledge base (and archivist guide), player notes, speaker map, glossary, corrections, DM questions and conversations. Every query is scoped by `campaign_id`; knowledge-base records are fetched with `id AND campaign_id`, so even a wrong id can't reach another campaign. Speaker links (on upload and in the speaker map) only take accounts in that campaign. Q&A only runs for a member of the campaign it was asked in, and the prompt names that campaign and the asker's character in it. A test asks in a second campaign with every tool and checks nothing from the first appears.

### 5.5 Privacy (primitive version)

Who-knows-what is decided by the archivist and enforced by the server:

| Data | Who can see it |
|---|---|
| Knowledge-base record | Its `known_by` (NULL = every member). DMs see all. |
| Transcript (search, read, evidence, `/transcript` endpoint) | Attendees of that session. DMs see all. |
| Player note (search, list) | **Only its author**, not even the DM. |
| Character sheet | **Only its player** on the page and through the API, not Q&A directly. A player's other characters (not the active one) too: only they list or open them (`GET /characters`); everyone else, the DM included, sees only the active character (2026-10-21). The DM sees only the parts in the Inventory row below (owner, 2026-10-10: "the DM should see this") and, on maps, a character's hit points like everyone in the party (§6.6). The DM has no sheet of their own (Creatures instead), and a DM sheet left from before is never sent to the archivist. The archivist reads it (§5.2) and keeps what's only on a sheet `known_by` that player, so Q&A can answer the player from it; but DMs see every record, so the DM can learn sheet details through Q&A (same as notes, below). The admin login has none. |
| Dice roll | Party rolls: everyone in the campaign. "Only the DM": the DM and whoever rolled (the DM's own is a secret roll). "Only me": whoever rolled. |
| Rest the DM called | The DM, and the players it was for (live); the list, to everyone in the campaign. Who got nothing from a long rest (at 0 hit points, from their private sheet): only the DM and that player. A hit die spent is a roll, shared like any roll ("Who sees my rolls"). |
| Handout | The DM, and the players it was given to (`to`: everyone, or chosen players). Its picture is served only to them. Players aren't told who else got it. Its text and what the AI read in its picture reach the archivist with who got it, so knowledge from it is known only by them. |
| Map | The DM: everything except players' private pins. Players: only maps the DM has shown them (to every player, or to them among chosen players: `shown_to`), and only the places on a map revealed to them (`revealed_to`) where they can see them, without a place's record, without the AI's description and reading notes, stat blocks, record links, hidden tokens, or tokens and other things under the fog (their page draws the fog over the whole picture from the walls and lights it gets: owner, 2026-10-14, a determined player could see the picture and the wall layout in their browser, and that's fine); NPCs' and enemies' hit points only as how hurt they look; they can change only their own tokens (their character, and the companions and summons they control, whose stat blocks only they get), and make them follow only tokens they can see (whom a token follows they get only when they can see that one too); whoever follows their token goes with it to another map. A player character's hit points on its token are its sheet's current and maximum (when the player has saved a sheet), shown to everyone who sees the token, as token hit points always were. Private pins: only their owner. The archivist gets what happened on maps players could see, without hidden tokens (§6.6 "Map events"); Q&A doesn't read maps. |
| Creatures | Only the DM (the Creatures tab and its API, and Ask when the DM asks: §5.3 step 3b). A token placed from one is an ordinary token: players see it like any other. |
| Inventory (equipped gear) | Like the sheet (it is part of it), except that the DM sees what each player has **equipped**: its name, how many, proficient or not, attuned, magic bonus, armour, the to-hit and damage it gives, what magic items do to the sheet, and the AC worked out (and whether the player typed their own AC); also the total weight carried against the campaign's limit (and whether they're encumbered) and how many items they're attuned to. Not what's only carried, nor the rest of the sheet (`GET /gear/equipped`, DM only). A player's item lookup never uses the DM's own items (they may hold secrets); it goes to the PHB tables, the books and the AI. |
| Items, merchants | The lists, notes and sales: only the DM. The sales say who bought what, so the DM learns some of what players carry (owner, 2026-10-10: fine). A player sees a merchant's shop (name, description, picture, what it sells, prices, how many are left, and each item's description and picture) only while one of its tokens is on a map they can see (shown, not hidden, in their sight); otherwise 404. Buying changes only the buyer's own sheet. A player gets the picture of one of the DM's items only through a shop they can see or while it's in their own inventory (bought there); nothing else of the item. |
| Wiki | Only the DM writes it. A player reads their own version (tab and API, stage 6a): only the pages and parts available to them, filtered on the server for every route (a player's `?as=` is always themselves); links to pages they can't see are only their words; templates, history, proposals and planned or false parts never reach them. Only the DM sees the AI's proposals and its wiki jobs (players' job lists leave them out). A proposed part is offered to the players who know every record it was written from (`known_by`); a change never widens a section; a reveal reaches only players who know the records behind it, and the DM approves each. Each page, section and `:::for` / `:::dm` block has who it's available to; the narrowest wins. Ask gives a player only the parts available to them (filtered live from the page, never from the index); other names are DM-only. |
| Archivist | Sees everything, including all notes; decides `known_by`. |

The archivist's rules: openly happened → attendees (everyone if all attended); only in a player's note → that player; whispered/secret perception → that player; absent players don't know unless told later (then widen); mixed records get split; when in doubt, restrict.

**Deferred:** the archivist currently includes the DM in `known_by` for records built from a player's private note, so the DM can learn note contents through Q&A or the debug view. The same now goes for what's only on a character sheet (DMs see every record). The DM can do what's built; more may come (owner, 2026-10-10). More privacy work is planned.

### 5.6 Performance

- Q&A latency matters; processing time doesn't (project owner's decision).
- Measured with the real archivist knowledge base: 5–10s per question, most answered without any tool calls thanks to pinned records and pre-search. First text ~1.5–2s (earlier measurement).
- A real archivist run on a ~3-minute sample took ~70–100s at high effort.
- Not done, by decision: changing the Q&A model, lowering Q&A effort, API fast mode. A warm Claude Code process would save ~0.6s; not adopted.

### 6.4 Character sheets

Owner's requirements (2026-10-06): structured like a normal 5e sheet; autofill what can be worked out from the core stats; **anything the player changes by hand must be respected and preserved**; saved between sessions; players can upload an existing sheet; a spells section with full spell details, which can be pulled in by name.

- **Several characters** (owner, 2026-10-21: "I want players to be able to have multiple sheets with multiple characters. Only one can be active at a time"). A player can have up to 20 characters per campaign, each a whole sheet of its own (`sheets/store.js`); one is **active**, the one they play. Everything that reads "the player's sheet" uses the active one, because it all goes through `sheets.get(campaign, player)`: the Sheet and Inventory tabs, their map token (its hit points, speed, height and picture; its name shows the active character's name), rests and hit dice, merchants' purchases, potions, class features, Wild Shape, the DM's Items tab, Review sheet, upload and download. Pictures belong to a character (`character_pictures.number`), so switching changes the token picture too.
  - **On the Sheet tab** (`web/public/sheet-characters.js`), above the sheet: a strip saying **Playing <name> · <race and classes>** and a **Characters (n)** button that opens the list (remembered per browser): each character with **Playing now** or **Make active**, **Rename**, and **Delete** (asked first; not for the one played: make another active first), and **+ New character** (a name, then a blank sheet with the player's name filled in, made active; the one played before is kept). A player with nothing saved yet has their blank first character; a new one then becomes character 1.
  - **Switching is the player's alone** (Claude's call): the DM doesn't see the list or change it, and sees only the active character (on the Items tab, on maps, and by name wherever players are named). Inactive characters stay private to their player: only `GET /characters` (the player's own) lists them.
  - **Who the player plays**: making a character active (or renaming the active one) sets the membership's character name (`auth.setCharacterName`, archived in `members.json`), so speaker names, Ask ("who plays …"), rolls and the archivist's roster follow; the admin can still type it.
  - **Two devices**: the page sends the character's number with each save (`PUT /sheet { character }`); if another character became active elsewhere, nothing is saved over it (409 `switched`) and the page shows the active one. Switches are sent live (the `sheet` event carries `number`) and between windows.
  - **Deleting** only hides a character (`deleted_at`); its archive files stay, and restore keeps it hidden. The archivist reads every character's changes, each marked as the one played now, not played now, or deleted, and is told each switch and deletion with its time (`<characters_changed>`, `kb/updates.js`).
- **Contents** (Sheet tab, `web/public/sheet.js`): page 1 (name, with a one-line summary such as "High Elf · Wizard 5 / Fighter 1 · Level 6"; class & level with multiclass rows, background, race, alignment, player name, XP, character level; ability scores; inspiration, proficiency bonus, saves, skills marked ○/●/◆ for none/proficient/expertise, passive Perception, other proficiencies; AC, initiative, speed, HP, hit dice (a row per die size with a tick per spent die, Spend and Short rest: §6.8), death saves; attacks; coins and equipment; personality, ideals, bonds, flaws; features); page 2 (details, appearance, allies, backstory, treasure); page 3 (spellcasting class and ability, save DC, attack bonus, slots per level and Pact Magic, each with a circle to tick per slot used; spells grouped by level with prepared ticks). Download (JSON), upload, print.
- **Attacks and spells that roll** (owner's request, 2026-10-09: "we want bonuses to apply. And we want spells to be handled too… a roll to hit option and a roll for damage option. If an attack is a saving throw instead, it just needs a roll for damage. Rolls for both should account for modifiers"). Worked out in `shared/src/rolls.js`, the same file for the page and the tests.
  - **An attack** (`normalizeAttack` in `sheet.js`) has a name, damage with its type ("1d8 slashing"), and under it: attack roll or saving throw; the ability it adds (Strength, Dexterity, …, Finesse = the better of Strength and Dexterity, Spellcasting ability, or As written = nothing); proficient or not (saved, on by default; since the Inventory there's no tick for it on the page, see below); a magic bonus. To hit = proficiency (if proficient) + the ability's modifier + magic; damage = the dice + the ability's modifier + magic. A saving-throw attack has no roll to hit: its DC is 8 + proficiency + the ability's modifier, against the save ability chosen, and its damage adds only the magic bonus. A number the player types in the to-hit or DC box is kept (blank = worked out; the worked-out one shows in the empty box), like every other automatic value. Typing one of the PHB weapons (`WEAPONS`, SRD) the character carries as a new attack's name fills in its damage and ability; "Unarmed strike" fills in 1 bludgeoning and Strength. The name box suggests "Unarmed strike" and the weapons in the inventory. Attacks saved before 2026-10-09 (and uploaded sheets) have no ability (As written), so their typed bonus and damage roll exactly as before. Under each attack the sheet shows what it will roll ("1d20+5 to hit · 1d6+3 piercing"). Damage with no dice (an unarmed strike's 1) is shown as a number, not rolled.
  - **Equipped weapons** (owner's request, 2026-10-09: "Players shouldn't have to choose proficiency each time… when they equip one… they should toggle if they are proficient in it or not. The DM should be able to see what they have equipped"): each weapon equipped in the Inventory tab (below) shows at the top of Attacks, worked out from the inventory line (it can't be edited there): name (×2 for two daggers), to hit, damage, a d20 to roll to hit (damage offered after, doubled on a natural 20), Dmg, and for versatile weapons 2H (one die size bigger: `gearRolls`). Proficiency comes from the inventory line, so typed attacks no longer have a Proficient tick (their proficiency is still saved and counts; attacks typed by hand are for anything that isn't an item: unarmed strikes, a breath weapon).
  - **Weapon attacks need the weapon** (owner, 2026-10-10: "Players can add attacks that use weapons not in their inventory"). A typed attack whose name names one of the PHB weapons (`attackWeapon` in `gear.js`: "Longsword", "+1 longsword", "Thrown daggers", "Shillelagh (quarterstaff)") needs an inventory line naming that weapon (`ownsWeapon`: "Dagger", "+1 Longsword", "Dagger of Venom"); unarmed strikes, spells, features and natural weapons don't. Without it, the row is marked, its roll buttons are off, and it says so with **Add a Longsword to my Inventory** (adds it from the tables, equipped, with Proficient from the class and the attack's magic bonus, and removes the typed row, since equipped weapons show in Attacks by themselves). The server refuses a save (400, naming the weapons) that adds such an attack or renames one to such a weapon (`newUnownedWeaponAttacks`, against the saved sheet); the page doesn't send it and says "Not saved: you don't have a Longsword in your Inventory…" until it's fixed. Attacks the saved sheet already had (sheets from before, uploaded sheets, a weapon later sold or dropped) stay and save, but don't roll until the weapon is back. Only PHB weapon names are recognised: a homebrew weapon's name ("Sunblade", "My sword") isn't checked.
  - **A spell** has: Roll (none, spell attack, or saving throw with its ability), damage or healing ("8d6 fire", "1d8 healing"), more dice per slot level above its own (for a cantrip: at 5th, 11th and 17th character level), and + spellcasting modifier. These are read from the spell's description when it's added or looked up, or for a spell saved before (`guessSpellRolls`: "make a ranged spell attack", "a Dexterity saving throw", "8d6 fire damage", "regains hit points equal to 1d8 + your spellcasting ability modifier", "increases by 1d6"), and the player can change them in the spell's details. In the spell's row: a d20 to roll the spell attack (spell attack bonus; damage offered after, doubled on a natural 20) or the DC for a save (spell save DC and ability), a slot level to cast it with (1st level and up: each level with how many slots are left, pact slots counted; the lowest with one left to start), and Dmg (or Heal); a spell with nothing to roll has **Cast**. Casting a spell of 1st level or higher spends the slot (owner, 2026-10-28: "Using a spell does not burn a spell slot at the moment"): the to-hit roll for a spell attack, the damage or healing roll for anything else, or Cast. The server spends it (`POST /campaigns/:cid/sheet/spells/cast`, `castWithSlot` in `shared/src/spell-slots.js`, the same rules as casting on the map); with none left at that level the page asks whether to roll anyway (a scroll, an item, a free casting). Cantrips spend nothing. Not handled: more darts or rays when cast higher (Magic Missile, Scorching Ray) and Eldritch Blast's extra beams; the player types those dice in.
- **Inventory** (the players' Inventory tab, `inventory` on the sheet, rules in `shared/src/gear.js`; owner's request, 2026-10-09: "Players should be able to search a weapon, similar to the creatures tab… not just weapons. Any items… equip multiple of SOME things. Two daggers, but not two armours"). Each line: name, kind (as the DM's items), how many, how many equipped, Proficient, needs attunement and Attuned, magic bonus (−5 to +5), weapon stats (damage with type, Strength / Dexterity / Finesse, simple or martial, properties) or armour stats (base AC and light / medium / heavy / shield), weight, description and where it came from. At most 200 lines.
  - **Adding** (tidied 2026-10-21, owner: "This should be cleaner… It always suggests weapons regardless of what category I select. And I feel like there should be some way to check an items stats before you add it"): one row, **Kind** (Any kind, Weapon, Armour, Gear, Tool, Potion, Scroll, Magic item, Other), the name, **Look up**, **Add by hand**. The kind decides the names suggested while typing (`itemNames` in `shared/src/item-names.js`: the PHB's weapons, armour, adventuring gear, tools and potions, spell scrolls and the SRD's magic items; Any kind suggests them all) and the kind Add by hand makes. Look up (or picking a suggestion) shows the item's **card** under the form before anything is added (`gear-card.js`): its kind, rarity, attunement, a weapon's damage and properties, armour's AC, type, Strength and Stealth, charges, what it heals, what it does to the sheet, weight, where it came from and its description rendered from Markdown, with **Add** and **Cancel**; the inventory line keeps the rarity and shows it. The lookup: the 37 PHB weapons and 13 armours (`WEAPONS`, `ARMOR`, SRD) come straight from the tables with no AI call, also with a magic bonus ("+1 Longsword", "Longsword +1"); anything else is looked up like the DM's items (§6.9: the group's books, then the AI's memory, counted in `SHEET_AI_PER_HOUR`) but never in the DM's own items (`GET /campaigns/:cid/gear/lookup?name=`; nothing is saved on the server until the sheet is). A weapon or armour not in the tables gets its stats read from the description (`itemStats`: "1d8 slashing", finesse, versatile, "AC 14", heavy). **Add by hand** adds a line of the kind picked beside it (owner, 2026-10-16: "the inputs should depend on the category") and opens its Details with that kind's fields: a weapon's damage, ability and magic bonus, armour's type, base AC (or a shield's bonus) and magic bonus, what a potion heals. Changing a line's kind swaps the fields (and keeps the details open). ### 6.5 Dice

Owner's requirement (2026-10-07): an animated dice roller like D&D Beyond's, as long as it looks exactly the same to the player. D&D Beyond lets the physics in the browser decide the roll; here **the server decides** and the dice are animated to land on its numbers, which looks the same, is evenly random, and can't be faked from the page (that matters once rolls are shared).

- **Rolling:** `POST /campaigns/:cid/roll` (anyone in the campaign) with notation (`1d20+5`, `2d6+1d4-1`, `d%`; d2, d4, d6, d8, d10, d12, d20, d100; up to 50 dice) and a mode. Advantage/disadvantage applies when the roll has exactly one d20: it's rolled twice and the higher/lower kept. Numbers come from `crypto.randomInt`. Parsing and the arithmetic are in `shared/src/dice.js` (the page uses the same file to read dice out of an attack's damage, e.g. `1d8+2 piercing`). Who sees a roll: "Sharing" below.
- **3D:** the dice are 3D and really thrown (physics), then their faces are relabelled so the face that lands up shows the server's number. A d100 is a tens die and a units die. Dice take the theme's accent colours. Off with reduced motion or when switched off in the tray; then the result just appears.
- **Rollers** (owner's call, 2026-10-08: "just keep the classic and deluxe 3D dice, scrap the rest"; Quick, Lite, Flat and None were removed). `DICE_ROLLER` in `.env` picks the default for everyone (`deluxe` unless set; sent to the page in `GET /me` as `dice.roller`); each player can pick the other in the tray (kept per browser; a saved choice that no longer exists falls back to the server's). `ROLLERS` in `dice.js`:
  - `deluxe` (default; owner's request, 2026-10-07: "a more fancy option, all the bells and whistles, then optimise it"): `dice-deluxe.js`, its own Three.js (0.186) scene with cannon-es physics, both served from the server's packages (`/vendor/three/`, `/vendor/cannon-es.js`). The throw is simulated in one go first (`dice-physics.js`, 120 steps a second, a few ms), then replayed, so no physics runs while drawing. Each die's numbers are turned by one of the solid's symmetries (`relabel` in `dice-shapes.js`, which also holds the d4 to d20 solids) so the server's number ends up on top (a d4 reads at its top corner). Looks: physical materials (clearcoat plastic, metal, see-through ice/glass, iridescent glitter) lit by a studio reflection map, tone mapping, soft shadows on the page, key and rim lights, engraved numbers (bump map), glowing numbers for fire/magic styles, a pulsing glow on a natural 20, natural 1 or max damage, and dice sounds timed to the recorded collisions (Web Audio, the library's sound files). Speed: textures cached per style; shaders compiled when it loads; the first frames measured, and quality steps down (resolution, shadow size, see-through, then shadows off) on a slow device or back up on a fast one, remembered per browser. ~1.7 s a roll.
  - `classic`: [dice-box-threejs](https://github.com/3d-dice/dice-box-threejs) as it comes (Three.js + cannon-es in one self-contained ES module, served at `/vendor/dice/dice-box.js`, sounds under `/vendor/dice/sounds/`; physics, shadows; ~3.5 s a roll: the library only counts dice as stopped after ~3.5 s of simulated time, whatever the hardware).
  If the chosen roller can't start (no WebGL, or its library fails to load), the other is tried, then the result just appears; the tray says so. The dice libraries (dice-box, Three.js, cannon-es) are sent compressed (brotli or gzip, made once per file, with an ETag so a repeat visit gets a 304): ~2.4 MB becomes ~0.4 MB. The chosen roller starts loading when the tray opens or the roller is changed. The effects canvas draws each particle from a picture made once per shape and colour (~17 ms a frame; blurring each particle as drawn took ~370 ms).
- **Dice styles and effects** (owner's request, 2026-10-07: "more dice themes, special effects, fancy stuff"): 24 styles in the tray (`STYLES` in `dice.js`: "Match the page" plus colour/texture sets, most adapted from the library's own; textures served from `/vendor/dice/textures/` and fetched only for the style in use). With Classic they use the library's plain or matte materials (its metal and glass need a reflection map the library switches off, so they'd render nearly black); Deluxe gives each style its own physical material. `dice-fx.js` draws on a canvas over the page: each style's trail behind every moving die (positions projected from the 3D scene each frame), a natural 20 (golden flash, rings, stars and confetti at the die, a banner, a shine on the result), a natural 1 (red flash closing in, smoke, a banner, the page shakes) and maxed damage (2+ dice, no d20, all on their highest face). Chimes are synthesised with Web Audio. "Try it" and picking a style throw a preview (rolled in the page, shown only, never recorded). Effects can be switched off; they're always off with reduced motion.
- **Page** (`web/public/dice.js`): the tray (dice buttons and a notation box, Normal / Advantage / Disadvantage for the next d20, dice style, roller, animated / effects / sound switches kept per browser, this session's rolls), the result card (total, every die with dropped ones struck through, natural 20 / natural 1, and a damage roll offered after an attack: doubled dice on a natural 20). On the sheet (owner's request, 2026-10-09: "a function to roll attacks from the character sheet, as well as other stats"), clicking a save, skill, ability name, initiative or spell attack rolls a d20 plus that value (the names that roll are underlined with dots); each attack and spell has a roll to hit (then its damage offered, doubled dice on a natural 20) and a damage roll, with the sheet's modifiers (§6.4 "Attacks and spells that roll"); death saves have one. Shift-click: advantage; Alt-click: disadvantage; or, with no keyboard (phones), the sheet bar's **Next d20** buttons (Normal / Adv. / Disadv., the same setting as the tray's, back to Normal after one d20 roll). Every one of these is an ordinary roll: the server rolls it, the chosen roller shows it, and it's shared like any other ("Sharing" below). **Initiative** from the sheet (`initiative: true` on the roll) also goes into every fight on a map the player can see where one of their player character tokens hasn't rolled yet (§6.6 "Initiative"); the result card says which map. A player's **Roll** button in the map's turn order is the same roll (d20 + the initiative on their sheet, worked out by the server).
- **Sharing** (owner's request, 2026-10-08): every roll goes into the campaign's roll log (`rolls` table, `label` saying what it was) and out live on the campaign's live stream (`GET /campaigns/:cid/live`) to whoever may see it. "Who sees my rolls" in the tray, kept per browser: Everyone (default), Only the DM, or Only me; for the DM, Everyone or Only me (secret). The tray's "Table rolls" list has the last 50 rolls you may see (yours and others', with the character's name, and a lock on private ones); someone else's roll also shows a short note at the top right. The server enforces who sees what. Rolls aren't archived and the archivist doesn't get them (owner's call if wanted).

### 6.6 Maps

Owner's requirements (2026-10-07): no premade maps. The DM imports their own map (a battle map, a town, a region, anything); the map itself is just the terrain. Since 2026-10-11 the DM can also **make a map from scratch** in the app (owner: "I also want to be able to create maps from scratch. Meaning we want assets! And a fully fleshed out map creator. The AI reads it when the DM asks (Map settings → Read with the AI; since 2026-10-16 not on import, owner: "That shouldn't be automatic") and turns it into something interactive. The DM then adds tokens by hand for characters, enemies and NPCs. **Players move their own token; the DM can move any.** Everyone sees moves live.

- **Import** (DM, Map tab): a PNG, JPEG or WebP image (up to the upload limit). The image is archived exactly as uploaded (`maps/<id>/image.<ext>`); the page shows that file. The map starts hidden from players.
- **Showing a map to the players** (owner, 2026-10-20: "Switching what map is showing should be seamless and easy", after his player's page stayed on the old map while the DM was on a new one): a map is **shown** (Map settings → Players can see this map) or not, and players can look at any shown map from their map list. The DM's **Show players this map** button, beside the map list (out in full screen too, in ⋯ on a phone), shows the map on screen if it was hidden and makes it **the players' map** (`POST .../bring` sets `brought_at`; `playersMap` in `shared/src/map.js`: the shown map brought to last). Every player's page goes there at once (the live `map` update carries the new `brought_at`) and says "Your DM brought everyone here" in its status line. On the players' map the button reads **Players are here**; the DM's map list marks it "(players here)", the players' "(party here)". Players can still look at another shown map; only the next bring moves them again. A player's page opens on the players' map (else the one they last had open, else the newest); when the map on screen is hidden it goes to the players' map, and back to the hidden one if it's shown again before they pick another. When the players would see only dark fog there (fog on, nothing revealed, and line of sight off or no player character on the map), the DM's status line says so and what to do. The archivist hears "The DM brought the players to the map …" (Map events).
- **A page of a PDF** (adventures and map packs often come as PDFs): the DM picks the page number. The server draws that page with pdf.js on a native canvas (`@napi-rs/canvas`), 3000 px on the long side (at most 6× the page's size), on white, and uses the PNG as the map's image. The PDF is archived next to it (`maps/<id>/source.pdf`) and the map records which page (`source`).
- **Reading (AI, in the background after import, or "Read again"):** the server makes a smaller JPEG copy (2000 px on the long side) and asks the AI (`maps` task) what kind of map it is, a name, a short description of the terrain for the DM, whether it has a grid (and roughly how many squares across and down), and its scale (from a scale bar or labels, e.g. "1 square = 5 ft" or "the map is 30 miles across"). Where the AI sees a grid, the server measures it exactly from the full image's pixels (`detectGrid`: edge strength per column and row, the repeat distance near the AI's estimate, then the offset), because the AI's counts are only approximate. A grid with no scale gets 5 ft per square. The DM can correct the grid (square size and offset, shown on the map while editing) and the scale. The map is usable while it's being read; a read interrupted by a restart is marked failed and can be run again.
- **Tokens:** the DM adds them with a kind (player character, NPC, enemy, companion or summon), a name, a size (Tiny to Gargantuan: ½, 1, 2, 3, 4 squares) and a colour. A player character token is tied to a player in the campaign (named after their character); that player can move it. It shows the token picture that player uploaded (§6.4), or initials until they do. The DM can give an NPC or enemy token a picture (owner's request, 2026-10-08): "Picture" on the selected token; if other tokens on the map have the same name (a pack of goblins), the DM is asked whether they all get it. The upload is archived as it came (`maps/<id>/tokens/<file>`); the token keeps `art: { file, type }`, which never leaves the server (the page gets `picture`, its key) and is served cut to a square around what stands out, only to people who can see that token. "No picture" goes back to initials. On a grid, tokens snap to squares; on a map without one they're placed freely, sized relative to the map. While dragging, the page shows the distance moved (5e counting on a grid: every square, diagonals included, is one square; straight-line distance otherwise).
- **Companions and summons** (owner's request, 2026-10-14: "If players have companions or summons, they should be tokens under the players control. Which also means their rolls and movement"): a token of kind `companion` belongs to a player (`user_id`), like their character's: a familiar, an animal companion, a steed, a conjured creature. The player adds one with **Companion** on the map toolbar (players only; the DM uses Add token: pick the player under "Who is it?" and tick "A companion or summon of theirs"): a name, size, maximum hit points and darkvision, and by default its stat block looked up with the AI as for the DM's tokens, except that a player's lookup never copies the DM's own creatures (they're the DM's). It appears where the player is looking if they can see that spot, else next to their character (a player can't place one under the fog). Up to 12 per player per map (`MAX_COMPANIONS`). The player moves it (walls stop it, as their character), changes its hit points and conditions, light and darkvision, and its name, size, colour, speed and stat block; **Dismiss** takes it off the map. The DM can do anything to it. Everyone who sees it sees its hit points in full, like a party member's; its stat block goes only to its player (and the DM). Its player sees what it sees (it counts as one of their tokens for line of sight, so a familiar can scout), opens doors next to it and takes it through links. **Roll** on the selected companion opens its rolls, read from its stat block (`statBlockRolls`): each attack's roll to hit (with its damage offered after) and damage, and the six ability checks; they go through the dice like any roll, labelled with its name. - **Walls and line of sight** (DM, drawn in **Edit map**; Line of sight is ticked in Fog & sight): walls are straight lines in image pixels (`walls`: `{ id, x1, y1, x2, y2, door, open, locked, secret?, revealed?, source, group? }`, up to 2000; `source` is `dm`, `ai`, `file` or `creator` (from a map made in the creator)); a door is a wall that can be open, and locked (players can't open it). An **obstacle** (`kind: 'low'`) blocks movement but not sight: a building drawn as its roof, a cliff edge, a fence. The DM drags to draw a wall or door (ends snap to other walls' ends, then grid corners, so walls join without gaps), draws a **curved wall** with Curve (drag from end to end, move to bend it, click) or a **round wall** with Circle (drag from the centre out), clicks to erase (a curve's pieces share a `group` and are erased together; walls PATCH `curve: {x1, y1, mx, my, x2, y2}` and `circle: {x, y, r}`, stored as pieces of about 10°, a circle as 36), and in Lock mode clicks a door to lock it. Outside the drawing tools, the DM clicks a door to pick it: the bar under the map says whether it's closed, open or locked, with Open/Close, Lock/Unlock and Remove (opening a door unlocks it; locking one closes it). **Secret doors** (2026-10-13): Make secret turns a door into one (`secret: true`, walls PATCH `secret: id`); players see wall there (it isn't in their `doors`) until it's found (`revealed`): the DM presses Reveal (`reveal: id`; Hide again shuts it and makes it wall to players once more), or someone opens it. The DM sees it dashed. Map events tell the archivist when one was found. Doors are drawn as doors, not coloured lines: posts at both sides of the doorway, a thick plank across it with a badge in the middle (a door, or a red padlock when locked, which players see too), and when open the door stands swung from its first end with a dotted arc. A player clicks a door to open or close it, only a door they can see (players get `doors`: the doors they can see, never walls), not locked, within a square and a half of their token (`POST .../doors/:wid/toggle`). **AI walls** (task `walls`: the maps model at `xhigh` effort by default, `MODEL_WALLS` / `EFFORT_WALLS`; in the background, `wall_draft` status) is deliberately thorough, since a map is set up once (owner, 2026-10-08: worth being expensive; 2026-10-10: `max` used about 30% of a session's tokens, so one level down). The AI sees the map with a **ruler** round it (ticks every 50 and numbers every 100 of 0 to 1000 on each side, faint lines across every 100) so it reads positions off it; it answers with straight walls and obstacles as polylines, **curves** as arcs (start, a point halfway, end) and **circles** (centre and a point on the edge), doors, lights and difficult terrain (purpose `map:walls`). Then it **checks** its draft: the draft is drawn over the map (walls red, obstacles green, curves orange, doors blue) and sent back with its data to be corrected (purpose `map:walls-check`). Maps over 1800 px wide or tall are checked in **close-ups** (up to 3 × 3, overlapping a little, each with a ruler in the whole map's positions); each close-up keeps what lies in its own part (by the middle of each piece), and a close-up whose check fails keeps the first draft there (the notes say so). The server then tidies straight walls (`tidyWalls` in `maps/read.js`): nearly level or upright ones (within 4°) are straightened, ends that nearly meet (1% of the long side, or a third of a square) are joined, and with a grid, ends within 0.3 of a square of a grid line are put on it. Curves keep their shape (only their two ends join other walls). So a draft costs 2 to 10 calls at xhigh effort. (Proposed, not merged: PR #33, the owner's request 2026-10-11, adds an effort picker beside AI walls, default the server's setting or low to max, kept per browser, sent as `effort` with the draft.) The draft replaces the AI's earlier one; walls the DM drew stay; AI walls show in another colour and can be cleared. **Progress** (owner, 2026-10-10: clicking AI walls gave no feedback): while it works, `wall_draft` carries `step` (`tracing`, then `checking` with `parts` and `parts_done` as each close-up's check comes back, then `tidying`) and `started_at`, updated live (`onProgress` from `mapReader.walls`). **The tracing so far is drawn on the map as it goes** (owner, 2026-10-16: "Makes it feel more like it's doing something and not hanging"): `onProgress` carries a `preview` (the first draft, with each checked close-up swapped in as it comes back), which replaces the AI's walls, lights, terrain, stairs and raised areas on the map like the finished draft does; when it ends, `finished_at` and, when done, `found` (counts of the walls, obstacles, doors, lights and areas of difficult terrain it kept). Players get none of it. On the page the button reads "AI walls: starting…" at once, then "AI walls: working…" with a spinner, disabled; a message over the top of the map (so it shows in full screen and outside Edit map) says what the AI is doing and how long so far, that it takes a few minutes and the DM can carry on; then "AI walls done: 12 walls, 3 doors and 2 lights in 4 min" with the AI's notes, or the reason it failed with **Try again**. The DM closes the done or failed message; it stays closed in that browser (`dndapp.map.wallNoteSeen.<map>`) until the next draft. **Walls from a file:** a Universal VTT file (`.dd2vtt` from Dungeondraft, `.uvtt`, `.df2vtt`; Dungeon Alchemist and many map packs export one) gives exact walls (`line_of_sight` and `objects_line_of_sight`), doors (`portals`, open if not `closed`) and lights (`range` in squares, half bright, half dim), with no AI (`maps/uvtt.js`). Imported as a map, its picture becomes the map, its grid is used exactly (the AI's reading doesn't replace it) and squares are 5 ft. Added to an existing map (Edit map → Walls from file, `POST .../walls/file`), it's stretched to fit the map's picture and replaces the walls and lights from an earlier file; the DM's and the AI's stay. **Hiding walls:** Fog & sight has a Show walls tick box (per browser): unticked, walls, obstacles and lights aren't drawn outside Edit map, for a clean map while playing; doors still show (they're clicked). With **Line of sight** (`fog.sight`) on as well as the fog, each player also sees what their own player-character tokens have a clear line to: a visibility polygon from the token's centre, cut by walls and closed doors (`sightPolygon` in `shared/src/map.js`). **Unseen parts** (`fog.map`): what players get outside their sight and the DM's reveals: `dark` (blacked out), `grey` (greyed out: dimmed) or `shown` (the map as it is); tokens there are hidden in all three. With **Remember explored** (`fog.memory`, on by default, only meaningful when dark), places a player has seen stay on their map dimmed: a grid of 128 cells along the long side per player per map (`map_explored` table, schema v10, database only: not archived, so a rebuild forgets it; the DM can "Forget explored"). A player sees a token only if it's in their sight or in a part the DM revealed (dim, explored areas don't show tokens). The DM's rectangles still apply outside sight. The server works out what each player sees for deciding which tokens, doors, links, templates and terrain they get, and marks explored places (`maps/sight.js`). The page draws the fog itself (`playerFogMask` in `shared/src/map.js`, the same code): players get the walls that block as plain lines (`walls`: `{ x1, y1, x2, y2, kind }`, closed doors and unfound secret doors among them, as wall), the lights (`lights`: placed ones and those carried by tokens they don't get), the DM's rectangles and `fog.explored` (rectangles of the cells they've seen). While a player drags their own token the fog follows it, from where it would land, unless a wall is in the way. `sightPolygon` buckets walls into a grid of cells and walks each ray through it, so a map with 2000 wall pieces takes milliseconds; lit areas are kept per set of walls and shared by every player. While the map is panned or zoomed the stage is its own layer (`will-change: transform`, cleared once it settles), so the fog isn't redrawn every frame. Players can't move their token through a wall, obstacle or closed door (a straight line from where it was); the DM can put any token anywhere. Each player sees only from their own tokens, not their party's.
- **Height** (owner's request, 2026-10-15, after a brainstorm: research in the Claude project, `research/elevation/`): the DM's **Raised area** tool in Edit map drags out a rectangle at the height in the box next to it (feet above the map's ground, −1000 to 1000; negative for a pit); a click on one gives it the box's height; Erase removes it (`raised`: `{ id, points, height, source }`, up to 300, `PATCH .../raised`). Each is flat on top; where they overlap the highest counts (`groundAt`). The DM sees their outlines and heights in Edit map. Tokens have a **height** (`height` in feet, set in the token's bar as Tall; empty: a player character's sheet Height, read by `parseHeight` and sent as `tall`, else by size: Tiny 2, Small and Medium 6, Large 10, Huge 20, Gargantuan 30) and an **elevation** (`elevation`, Up in the bar: feet above the ground under it, for flying or climbing); players set their own. A token not on the ground shows ↑25 or ↓10. **Sight over heights** (the standard terrain line-of-sight test, as GIS viewsheds and Foundry's height modules do it): with line of sight on, a player sees a token only if, as well as being in their sight, one of their tokens has a line from its eyes (1 ft below the top of its head) to the top of the other's head that clears every raised edge it crosses: at each edge, `eye + (head − eye) × how far along ≥ the edge's higher side`. So someone on a roof is seen from far enough away but not from under its edge, the ground behind a building is hidden, tall and flying creatures see and are seen over lower things, and it's the same both ways. The DM's reveals show tokens whatever the heights. Walls still block whatever the height. Players get the raised areas (`raised`: `{ points, height }`), and their page's fog over heights (`heightShadows`) comes in **two shades** (owner's choice, 2026-10-20: a tall creature up on a roof is seen before a short one): clear where one of their tokens sees the floor, a light shade (`glimpse`, 30%) where none does but one would see a Medium creature standing there, fog where they'd see neither; so a roof seen from below is lightly shaded. It's outlined smoothly like a wall's shadow (owner, 2026-10-20: whole squares looked blocky beside the walls' shadows): points a square apart, then an eighth of a square apart where those differ, traced into outlines (marching squares) whose crossings are found by halving to a hundredth of the step, sent as `{ fill, rings }` and filled even-odd; explored places stay dim. ### 6.8 Rests and hit dice

Owner's request (2026-10-09): "a long rest and short rest feature. And a way to spend hit die." Also needed for merchants restocking "every x number of long rests". Defaults picked by Claude: 5e rules for the group's edition; the DM calls long rests for the party; players take short rests and spend hit dice themselves, rolled through the dice roller.

- **Rules** (`shared/sheet.js`: `hitDicePool`, `hitDice`, `spendHitDie`, `shortRest`, `longRest`, all pure, the server applies them):
  - **Hit dice** are kept per die size: `hit_dice_spent` `{ "10": 2, "6": 1 }` (replaces the single `hit_dice_used` number; an old sheet's number is counted from the biggest die down). The pool is read from the Hit dice box, so a typed value ("5d8") counts. Sizes d4 to d12 and d20.
  - **Spending one:** roll the die plus the Constitution modifier; regain that many hit points (never fewer than none), up to the maximum. A blank Current hit points counts as full.
  - **Short rest:** Pact Magic slots come back, and class features that come back on a short rest (§6.4: all of them, or one for the 2024 rows that say so, like Rage, Second Wind and Wild Shape); the player then spends hit dice.
  - **Long rest:** all hit points back, temporary hit points gone, every spell slot, Pact Magic slot and class feature use back (except rows reset by hand), death saves cleared, spent hit dice back: up to half the character's total (at least one), the biggest first, under the **2014** rules; all of them under **2024**. Under 2014 a character at 0 hit points when it starts gets nothing from it. Exhaustion isn't on the sheet, so it isn't touched.
  - **Edition:** the campaign's rules edition (§6.10, `editions.js`): the DM's setting, else `REST_RULES` (2014 or 2024), else the group's Player's Handbook in the books folder (§5.3) when it is exactly one edition, else 2014 (the sheet's own rules are 2014).
- **Players** (Hit dice box on the sheet): a row per die size with ticks (editable by hand, like the slots) and how many are left; **Spend** calls `POST /sheet/hit-dice`, where the server rolls through the roll log (`rolls.js`, so it's shared by the tray's "Who sees my rolls" and the dice animate), applies it and saves the sheet with the reason; **Short rest** calls `POST /sheet/short-rest`. Unsaved typing is saved first. The DM has no sheet, so no hit dice.
- **The DM** (Rest button in the header, `web/public/rests.js`): ticks for each player (all by default), Short rest and Long rest, which rules apply, and the last rests. `POST /rests` changes every sheet in it (players with no sheet yet are still counted), each saved with the reason ("long rest (called by the DM, 2014 rules)") and `by` the DM, so the archive and the archivist see why.
- **Live:** the rest goes out on the campaign live stream (`rest`) to the players in it and the DM. A player's page shows a note and reloads the sheet (with unsaved changes, saving them meets the newer version and the usual conflict question applies); other windows with the sheet follow (BroadcastChannel).
- **Kept and counted (the hook for other features):** each rest the DM calls is source data, archive first (`rests.jsonl`, one line each: `{ id, kind, at, by, edition, user_ids, skipped }`), mirrored in `rests` (schema v13) and restored. In the server, `rests.events` emits `'rest'` with the rest and its `campaign_id` after the sheets are saved, and `rests.count(cid, { kind: 'long', since })` says how many long rests have been called after a time, so something that happens "every N long rests" (a merchant restocking) can keep the time it last happened and count, or react to the event. Players' own short rests aren't in the log.
- **Not changed by rests:** NPC and enemy tokens' hit points, item charges (owner, 2026-10-10), and anything the archivist knows. Player character tokens show the sheet's hit points, so they follow (§6.6).

They start from what the app reads (the PHB tables by name, else the description, `itemStats`), and are saved as the item's own (`stats`, `normalizeItemStats` in `shared/src/gear.js`, only the parts of its kind) once the DM changes one; until then the item keeps being read from its description. A buyer's inventory line gets them as they are (`addToInventory`), so equipping a bought armour sets the AC with no reading of the text. The item's card shows them ("AC 15 · heavy · +1 (set by you)"). Fill in clears them (a new description is read again). The player can still change any line, and a typed AC on the sheet still wins (the DM may overrule the rules). **Pictures** (owner, 2026-10-10: "Items should have pictures"): the DM uploads one (New item, or Picture on a card), Find online brings one, and Look up and Fill in bring none. The picture shows on the Items tab, in a merchant's shop, in the Inventory of a player who bought it (`GET /campaigns/:cid/gear/pictures`, `GET /campaigns/:cid/gear/items/:iid/picture`: only items in the asker's own inventory, kept even after the DM takes the item off the list) and in the DM's equipped list. Lines a player adds themselves have no picture. Below the list, **What the players have equipped** shows each player's character, AC (marked when they typed it themselves) and equipped items with to hit and damage, not proficient, attuned (`GET /campaigns/:cid/gear/equipped`; loaded with the tab, and Refresh), so the DM can check for cheating (§6.4). Equipped items that are the DM's own (bought from a merchant) show their picture there.
- **Merchants** (the DM's Merchants tab, `src/merchants.js`, `web/public/merchants.js`): a name, a description players see, notes only the DM sees, a token colour (gold by default), a picture, open or closed, and **stock**: lines of an item, its price here (the item's usual price unless the DM sets one), how many are left (or no limit) and a **restock level** (by default what it started with; empty: restocking leaves it alone). The DM changes a line's price and levels, stops selling it, restocks by hand ("Restock now"), sees what players see ("See shop"), and sees the last 50 sales (who, what, how many, for how much).
- **On the map:** "Place on map" puts a token in the middle of the view: an NPC token with the merchant's name, colour and picture, and `merchant: <id>` (players can't change it). It has a gold ⚖ badge. Clicking it (anyone who can see it) shows a **Shop** button. Closing the merchant down leaves its tokens as ordinary NPCs.
- **Buying** (players, `POST /campaigns/:cid/merchants/:mid/buy` `{ line, qty }`): the shop shows what each costs, how many are left and the coins on their sheet. The page asks once, saves anything waiting on the sheet, and the server then, with no waiting in between (so two buyers can't both take the last one): checks the shop is open and has enough; takes the price from the sheet's coins, big coins first, breaking a coin and giving change in gold, silver and copper if needed (`payCoins`; refused, saying what it costs and what they have, if they can't afford it); adds the item to the sheet's inventory (§6.4: a new line with its weapon or armour stats and Proficient from the class, or more of a line already there for that item or name; `addToInventory` in `shared/src/gear.js`); saves the sheet as a new version with the reason ("bought 2 × Potion of Healing from Mira for 100 gp"), so it reaches the archivist like any sheet change; and lowers the stock. The sheet on screen (and in a popped-out window) shows the new version. The DM can't buy (no sheet). Not built: selling items back.
- **Restocking:** a merchant can restock every N long rests (`restock.every`). Each line with a restock level and fewer left goes back up to it (never down). Each long rest the DM calls (§6.8; one call is one party rest) counts: `context.js` listens to `rests.events` and calls `merchants.longRest`, which keeps the count and the last rest and restock times on the merchant (archived with it). Short rests don't count, and players can't long-rest on their own.
- **Live:** any change to a merchant (a sale, a restock, the DM's edits) sends `merchant {id}` on the campaign's live stream; an open shop and the DM's list look again.
- **Archive:** like creatures: `items/<id>/` and `merchants/<id>/`, the whole entry after each change, pictures as uploaded; restored on start-up. The archivist doesn't read them; purchases reach it through the sheet changes.
- **Later:** selling items to merchants; haggling or prices per player; the archivist hearing about sales directly.

### 6.11 The DM's wiki

Owner (2026-10-18): "I want to start work on the DM being able to build a wiki. Our big selling point here is the AI, but of course manual changes and additions should also be possible." Research and options: `/mnt/project-files/research/wiki/campaign-wiki-research.md` (project files). Decisions (2026-10-20): the DM only at first, sharing "at a granular level"; separate from the archivist's records, but Ask reads it; a section the DM edits stays the DM's; the AI's page changes wait for approval; players can't write; the AI suggests reveals and the DM clicks; "If the part of the wiki is available to the players, then their ask should use it."

- **Pages** (`src/wiki.js`, `routes/wiki.js`, `web/public/wiki.js`): title, other names (aliases), kind (free text with suggestions: npc, place, faction…), inside another page (no loops; a deleted page's children move up), tags, and sections (heading, text, `by`: dm or ai, available to). Names are unique across titles and other names; renaming keeps the old title as another name so links keep working. `[[Page]]` and `[[Page|text]]` link pages; a link to a missing page offers to make it; a page lists what mentions it.
- **Available to** (`shared/src/wiki.js`): a page and each section are "only the DM" (a new page's default), "everyone" (a section's "same as the page") or chosen players. Inside a section's text, `:::for Thorin, Mira` … `:::` and `:::dm` … `:::` mark a block (by character or account name; an unknown name reaches no one and the page warns). What a player gets is the narrowest of page, section and block.
- **Saving** needs the version the editor opened (else 409: someone else saved first). Every save is archived whole (`wiki/<id>/changes.jsonl`), so History lists every version and any can be brought back as a new one. Delete takes the page off (the archive keeps it).
- **View as** a player shows exactly what Ask can tell them from the page.
- **Search index:** each part is indexed as a `wiki` doc with `visible_to` its audience; other names as a DM-only doc. Re-indexed on start-up restore and on a rebuild.
- **API** (DM only): `GET/POST /campaigns/:cid/wiki`, `GET/PUT/DELETE /campaigns/:cid/wiki/:pid` (`?as=<user id>` for View as), `GET …/history`, `GET …/history/:version`, `POST …/restore`.
- **The AI's changes** (owner, 2026-10-21: "Start on them"; `src/wiki-ai.js`, the "The AI's changes" view of the Wiki tab). After every archivist run (session, correction, sheets and handouts; `WIKI_AUTO=off` turns this off) a `wiki` job reads what the archivist changed since last time (`kb_journal`, 25 records per AI call, task `wiki`: `MODEL_WIKI`, `EFFORT_WIKI` medium) with every page's title, the pages those records are about in full (named in them, or found by searching the wiki), what's waiting and what the DM rejected, and proposes: **new pages** (one per person, place, faction, item, quest, and one per session), **changed sections**, **new sections** and **reveals**. The DM can also press **Read the records now** (for a campaign that had sessions before the wiki).
  - **Who it's available to** is worked out by the server: a proposed section goes to the players who know every record it cites (none valid: only the DM); a new page is as wide as its widest section; a change never widens a section (it can narrow it); a **reveal** offers a section to players who can't see it yet and who know the records cited, and approving it widens the section (and the page, keeping its other sections as they were).
  - **Approving:** Approve, Edit then approve (the edited section is then the DM's), or Reject; Approve all. A section the AI wrote says so on the page and stays `by: "ai"` until the DM changes it (in the editor or by editing a proposal), then it's the DM's for good; for a DM section the AI only makes a "suggestion" when the records disagree. A newer proposal for the same thing replaces one still waiting; a rejected one isn't made again (and the AI is shown it).
  - **Archive and rebuild:** proposals are archived whole after each change (`wiki/proposals.jsonl`) and restored; how far the AI has read is derived, and a rebuild moves it to the end, so replaying every session proposes nothing.
  - API (DM only): `GET …/wiki/proposals`, `POST …/wiki/proposals/run`, `POST …/wiki/proposals/:id/approve` (`{ title?, kind?, page_available?, sections?: [{ heading?, text?, available? }], players? }`), `POST …/wiki/proposals/:id/reject`, `POST …/wiki/proposals/approve-all`. `GET …/wiki` also gives `proposals` (how many wait) and `ai_run` (the last wiki job).

Null (the default, and every campaign from before) is "Day 14, 18:30" as always. Presets: Harptos (festival days named on their own, Shieldmeet every fourth year, Selûne full every 30.4375 days, seasons), Gregorian-like (Gregorian leap years, weekdays, a 29.53-day moon), Exandria (written from memory) and the DM's own, all editable in Campaign settings → Calendar. The clock stays minutes since day 1 began; `start` names day 1. `clockText(minutes, calendar)`: "3 Mirtul 1492 DR, 18:30 · Full moon" (only full and new moons are mentioned; with more moons, by name). Every clock text uses it: the map's clock and its dialog, travel, rests' notes, the wiki bar and the map events the archivist reads (`PIPELINE_VERSION` 31).
- **When, and events** (stage 4b; `shared/src/wiki-time.js`): a page has `when` (`{ text, from, to } | null`) and `events` (`[{ id, when, text, available, canon, truth?, owner?, sources?, by? }]`, up to 100). Times are minutes of the campaign's clock (0 = the start of Day 1; earlier is negative); `to` is where it ends (the same as `from` for a moment); both are null when the text isn't a time the parser knows, and the text is kept. The DM (and later the AI) writes only the text; the server reads it with the campaign's calendar and clock when it's saved (`parseWhen`), and keeps the time while the text stays the same, so "300 years ago" doesn't drift as the clock moves. Understood: "Day 12", "Day 12, 21:00", "Day 12 night" (dawn, morning, noon, afternoon, dusk, evening, night, midnight), calendar dates with or without the year, era, weekday or a time, whole months and years, festival days, ranges, "N years/months/tendays/weeks/days/hours ago" (from now), "N … before" (before Day 1), "today". `whenText` writes a time back by the calendar ("3 Mirtul 1492 DR dusk", "Mirtul 1492 DR", "1192 DR"; with no calendar before Day 1, "300 years before Day 1"). A player never gets a planned event or one not available to them, and gets a falsehood as a rumour; the search index and Ask's reading of a page list the events dated. The page shows its time under the title and its events in order (undated last); the editor shows what each time reads as while it's typed.
- **The Timeline** (stage 4c; `#/timeline`, `#/timeline/<page id>`; `web/public/wiki-timeline.js`, server `src/wiki-timeline.js`, `GET …/wiki/timeline?as=&truth=1`): pages with a time and every event, worked out for the viewer from the pages they may see (a player never gets a hidden page, a planned event, one not available to them, or a place not revealed to them). Lanes: the DM's own (`wiki: { lanes: [page ids] }` in the campaign's settings, up to 12; a lane holds its page, the pages inside it and the pages linking to it), then **History** (anything that began before Day 1) and **The campaign**; an item goes in the first lane that claims it, and an empty History is left out. Pages are picture cards, events slim bars styled by truth (a rumour dotted, false or planned faint) and by who wrote them (your notes striped). Dragged sideways, zoomed from centuries to hours; the scale says the calendar's years, months and days (or Day N) and marks full moons; a line marks now. Undated items and session pages with no time sit in trays. A card has Open page and Show on the map (the Atlas at the place, its pin pulsing); the Atlas card's On the timeline goes back. On a phone it's a vertical ribbon. The compass's When mini-ribbon and the Home's Timeline tile open it. At most 600 items.
- **The AI dates things** (stage 4d): `set_when` (a page's time; a session page's is the in-game span it covered) and `add_event` (a dated line on the page it's most about, linking the others, with canon, sources and who it's for from `known_by`), in the campaign's calendar; a new page can carry both. The DM approves each on Waiting (Time and Event cards, editable). **Journeys** on the maps are bars on The campaign lane, worked out from the maps' archived changes (never stored twice; for a player only maps shown to them and tokens not hidden).
- **Templates** (stage 5a; `#/templates`): a new page starts from its kind's template (the DM's own first, then the app's starters: Person, which leads with **At the table**, Place, Faction, Item, Creature, Quest, Session, Lore, Clue, Arc), with writing prompts in its empty sections and facts; sections left unwritten aren't kept. The DM's templates are pages with `template: true`, always the DM's and kept out of the wiki (its list, Ask, the views, the AI, maps and players). Any page can be saved as a template.
- **The AI as a writing partner** (stage 5b; on the DM's buttons, one AI call each, task `wiki_draft`; results wait under Waiting like the AI's other changes): **Draft from the records** (fill a page, or a new one with its template's prompts, from what the records say, with audiences from `known_by`), **Expand** a section (from the records; never wider), **Tidy** a section (the wording only; who it's available to stays), **Make up…** (in Find and on the Home: an NPC, a tavern, a shop, a rumour, a name, consistent with the wiki, which it reads first; a page only the DM sees, marked planned). **Link it**: names in a page's text that match another page are underlined, and one press makes the link (matched on the server, no AI).
- **Players read their own wiki** (stage 6a; the owner's plan assumed yes): the Wiki tab is everyone's. A player's wiki is the DM's filtered to them on the server (`wiki.listFor(cid, viewer)`: each page through `filtered()`, a parent they can't see dropped, and `[[links]]` to pages they can't see turned into the words shown, so a hidden title never leaks); every read route (`GET …/wiki`, a page, the Home, the Wheel, Find, the Web, the Timeline, the Atlas, the compass, the evidence) treats a player as `?as=` themselves, a hidden page is a 404, and the Atlas only lists maps shown to them. The page leaves out the DM's tools: New page, Templates, Waiting, the truth switch, Edit, History, View as, Save as a template, Delete, Make up…, Link it, and who a part is available to; the DM's addresses open the Home instead. Ask's names come from `listFor` too.
- **Character pages** (stage 6b): a page can be a player's character's (`player`, one page per player, only a player of the campaign). Waiting offers one for each character with a name and no page (`characters` in `GET …/wiki/proposals`; `POST …/wiki/characters {player}` makes it: the character's name, kind `character`, for everyone, with a copy of their token picture). The page shows **From the sheet** (`from_sheet` with the page: race, class and level; age, height, eyes and the rest with the appearance text; backstory; allies; `sheetParts` in `shared/src/wiki.js`), worked out from the active sheet on every read and never copied into the wiki. The sheet is private, so the DM and the player see every part and the other players only those the player shares (`sheet_share`, saved with `PUT …/wiki/:pid/sheet-share`, by the player or the DM). The party in the middle of the Wheel and on the Home opens their pages.
- **Players' lore** (stage 6c; owner, 2026-10-27: players may contribute lore about their own characters): on their character's page a player has **Your story** with **Add to your story** (`POST …/wiki/lore`, players only): a section on their character's page, a page of its own (inside their character's), a relationship (a fact) or an event, each for only the DM (the default), the DM and chosen players, or everyone. It becomes a proposal (`from: 'player'`, `by_player`) under Waiting, marked as from them, where the DM approves it (edited or not) as **their account** (`told`, the default), **true**, or **false** with the truth beside it, or rejects it; `GET …/wiki/lore` shows the player theirs and what became of each. Approved parts are `by: 'player'` with `owner`; only their player can change them (`PUT …/wiki/:pid/lore`, at once, and one the DM confirmed as true goes back to being their account); the DM changing one makes it the DM's. The AI never rewrites them (no update_section, Expand or Tidy on them; its instructions say so; a tie of theirs is never replaced). Ask already gives them as "Thorin's account". `PIPELINE_VERSION` 34. The page offers Change on a player's own sections; their facts and events change through the API for now.
- **Clues and reusable secrets** (stage 7a): `[[!Page title]]` (`EMBED_RE` in `shared/src/wiki.js`) puts that page's opening section (a clue's "what the players find", from the Clue template) where it's written, boxed, titled "Clue: …" with a link; the DM also sees who has it. Who sees it is the embedded section's own business, so making it available once shows it everywhere it's embedded. The server sends `embeds` with a page (`embedsIn` in `src/wiki-views.js`, from the pages that viewer may see); for a player an embed they can't see is removed from the text (`listFor`), with no trace (not its title; a section that was only that embed goes too). An embed counts as a link (mentioned in, the compass, the Web). Search, excerpts and the AI's reading leave embeds out (`unlink`); the embedded page is indexed on its own. Embeds inside an embedded page aren't followed.
- **Arcs and the prep page** (stage 7b): an arc is a page of kind `arc` with its quests and sessions inside it (its compass lists them); the Timeline's **Lanes by arc** gives each arc a lane. A prep page is a page of kind `session plan`, from the **Session plan** starter template (Strong start, Scenes, Clues (one `[[!Clue]]` a line), People, Places, Encounters, Treasure; facts Session, Arc, Played; all the DM's and planned). The **open** prep page is the newest whose Played fact is empty (`openPrepPage` in `shared/src/wiki.js`); the DM's Home has `prep` and a **Next session** tile that opens it, or starts one from the template. A prep page is never the Home's "last time". On a prep page, **Prep board** lays out the pages it names as cards, its clues first, then by family (`web/public/wiki-prep.js`; the boards of stage 10 will take over). Encounters link creatures and maps until stage 9's embeds.
- **After the session** (stage 7c): when the wiki's AI reads a session (`wikiAI.chronicle`, a run named "session N"), it also checks the open prep page's embedded clues (one more call, purpose `wiki:prep`, `PrepSchema`, the prep page, its clue pages and the session's records). For a clue that came out it proposes a **reveal** of the clue's opening section to those who found it (only players the cited records say know it, like any reveal) and the clue's **Found** fact ("session 12: Thorin, Mira", DM only); it proposes **Played** on the prep page, and the **next prep page** ("Session N+1 plan", the DM's, planned: a strong start from where it ended, the scenes not reached, the clues not found as `[[!Clue]]` lines, the Arc carried). All of it waits under Waiting. On a prep page the DM sees each clue's outcome (`prepMarks`): ✓ found (by whom), ↷ carried (to which plan), ✗ missed. If the check fails, the rest of the AI's run still stands and its message says so. `PIPELINE_VERSION` 35.
- **The quest board and lists (stage 8a):** `#/quests` shows the quests the viewer may see in columns by their Status fact (Rumoured, Active, Done, Failed, others, none), a row per arc; the DM moves a card (drag, or pick its status) and the Status fact changes. The DM saves a Wheel filter as a list, or has the AI make one from plain words (Ask's model, quick); lists show on the Home as rows of cards, are the DM's alone (kept with the proposals, never in the settings players get), and filter per viewer.
- **Who knows what and the spoiler check (stage 8b):** `#/knows` shows the DM every page against every player (all, some or none of it); a click shows that player's version, and chosen parts are revealed to them in one go. Before a reveal, a section sent as a handout, or approving a reveal or a player's lore, the server lists what the newly visible words name that those players can't see yet, so the DM doesn't give a secret away by its name.
- **Tidy up (stage 8c):** `#/tidy` lists what needs a hand, each with a button to fix it: links to missing pages, facts linking deleted pages, names not linked, pages with no links, places not on a map and places with no page, people with no picture, blocks for unknown names, parts planned for three sessions or more, and players' accounts not yet judged.
- **A Home that thinks (stage 8d):** after each session the wiki's AI also notes loose threads, a Previously on… recap to read aloud, and pages the records contradict. They show on the DM's Home with Open, Dismiss and (for a contradiction) Propose the fix; one dismissed is never raised again.
- **Live embeds (stage 9a):** `[[creature:Name]]`, `[[item:…]]`, `[[merchant:…]]`, `[[handout:…]]` and `[[map:…]]` in a page's text show the thing as it is now (a stat block with its rolls, an item's card, a shop to open, a handout, a map to open), never a copy. A player gets one only when they could see it anyway (a merchant whose token they see, a handout they got, a map shown to them; never a creature or an item) and loses the rest from the text, names included. The editor's + Embed picks one.
- **Import and export (stage 9b):** the DM imports a Markdown or Obsidian folder (a zip) straight into pages, only for them: front matter for kind, tags, aliases and facts, links kept, pictures into the wiki's, folders as "inside", existing titles never overwritten. Messy notes (pasted, text or a Word file) go to the AI, whose pages wait under Waiting. Anyone downloads the wiki as Markdown as they see it (the DM also as any player), and it imports back. Pages print one a sheet, alone or a chosen set.
- **Boards (stage 10):** a board is a canvas of cards (pages, sticky notes, wiki pictures, links to other boards) and labelled arrows, panned and zoomed, saved as it's moved (schema v21, archived per board). The DM's boards are every DM's; each player makes their own from the pages they can see (their conspiracy board), and the DM reads one only when they share it. A card for a page the viewer can't see (any more) is drawn as gone, with nothing about it. On a phone, boards are for looking and moving. A prep page lays its pages out as a board.
- **As of (stage 11):** the Atlas and the Web have a slider back to the end of each session played: the pages as they were then and where the tokens stood, worked out from the archive (never stored twice). A player sees only what they could see then and can still see now. The Timeline can give each player character a lane of their journeys.

## 7. Security & cost controls

- **Accounts:** no self sign-up. The server admin creates accounts, sets passwords and assigns roles on the admin screen (`/admin/*` routes, admin login only); the DM role can't. The console only does `init` (create the admin login), `set-password` (recovery) and `list`. Accounts with history can only be blocked, not deleted (the archive refers to them by id). Names are unique (ignoring case). Passwords: at least 6 characters, stored as scrypt hashes, never in plain text, including the archive.
- **Must change password at next login** (`users.must_change_password`, schema v4): set by the admin (default on for new accounts in the UI; optional on resets; toggle per account). While set, the server only allows `/me`, `/logout` and `POST /account/password` for that login (403 otherwise), so it can't be skipped by the client. The player gives their current password and a different new one; this clears the flag and ends their other logins. `POST /account/password` also works any time ("Change password" in the header).
- **Logins:** `POST /login` returns a random token (stored hashed in `logins`). It lasts `LOGIN_DAYS` (30) since last use; logging out ends it; a password set by the admin, or a block, ends all of that account's logins (changing your own ends all but the current one). After `MAX_FAILED_LOGINS` (10) wrong passwords for a name in 15 minutes, that name is refused for a while. Unknown names take as long as wrong passwords, so names can't be probed by timing.
- Role checks are server-side. Account and campaign names are cleaned (trimmed, repeated spaces collapsed) so stored names match what the page shows.
- AI credentials exist only on the server. Claude Code runs are locked down (§3.5).
- Privacy filtering is enforced in the server's tools and endpoints, not left to the model's discretion (§5.4, §5.5).
- Per-player Q&A rate limit; tool-call and cost caps per question and per archivist run; monthly spending cap on the API provider. Every AI call is logged in `llm_usage`.
- Back up `data/archive/`. The database can be rebuilt from it.
